# Engagement Finance Toolkit

A synthetic-data toolkit that simulates the financial operations of a mid-size professional
services practice running multiple concurrent client engagements -- portfolio setup, time &
expense tracking, budget-to-actual monitoring, draft invoicing, and (the core of it) systematic
data-quality and discrepancy detection, rolled up into a formula-driven Excel workbook.

It's built to demonstrate **engagement/account finance operations** specifically -- the
financial discipline of running individual client-billed engagements inside a services
practice -- not generic corporate FP&A.

> **This project uses entirely synthetic data.** All clients, engagements, staff, dollar
> figures, and findings are fictional and generated by this codebase for portfolio/demonstration
> purposes. No real organization's financial data is represented anywhere in this repository.

## What "engagement finance" actually means

In a professional services firm -- consulting, advisory, audit -- the client relationship isn't
"we sold a product," it's "we're delivering a contracted scope of work, staffed by named labor
categories, billed against a specific contract mechanism, over a defined period of performance."
Each engagement is effectively its own small P&L with its own budget, its own billing rules, and
its own compliance obligations to the client.

An **engagement (or account) finance associate** is the person keeping that machinery honest,
month over month, engagement by engagement:

- Is the team staying within its budgeted hours and dollars, by labor category?
- Is time and expense data complete, accurate, and approved before it reaches a client invoice?
- Is everything the team has earned actually getting billed, and on time?
- Is spend against a contract ceiling authorized -- and if it's not, does someone need to know
  *today*, not at contract closeout?

None of this is abstract financial analysis. It's operational hygiene applied to billing and
budget discipline, and it's the day-to-day of the role this toolkit is modeling.

## Why contract type is the organizing idea

Three billing mechanisms are modeled here, all common on government/public-sector engagements,
and each one changes what "healthy" looks like:

| Contract Type | How it's billed | Where the risk sits |
|---|---|---|
| **Time & Materials (T&M)** | Actual hours x labor-category bill rate, up to a not-to-exceed (NTE) ceiling | Firm risks unbilled/unauthorized hours past the ceiling |
| **Fixed-Fee** | A set price per milestone/deliverable, independent of hours worked | Firm risks cost overrun without recovering more revenue |
| **Cost-Plus-Fixed-Fee** | Allowable cost (labor at *cost* rates, not bill rates) + a negotiated fee | Ceiling is priced in cost terms, not commercial rates -- a distinction the toolkit deliberately gets right (see `budget_actual.py`) |

Getting the billing mechanics right per contract type is what separates this from a generic
budget tracker: the same $500K of labor effort means something completely different on a
fixed-fee engagement (a margin problem) than on a T&M engagement (a billing problem) than on a
cost-plus engagement (a cost-recovery problem).

## What each module does, and what it catches

```
src/engagement_finance_toolkit/
    engagement_setup.py         Portfolio, contract terms, role budgets, milestones, staffing
    time_expense_tracking.py    Synthetic timesheets/expenses with injected data-quality errors
    budget_actual.py            Utilization, rate realization, earned-value budget/schedule status
    invoicing.py                Draft invoices (T&M / fixed-fee / cost-plus), source reconciliation
    discrepancy_detection.py    The QC rules engine -- the module this whole project is built around
    reporting.py                Formula-driven Excel workbook with native charts
    run_pipeline.py             End-to-end orchestration
```

### `engagement_setup.py`
Generates a synthetic 18-engagement portfolio (7 T&M / 6 cost-plus / 5 fixed-fee -- a
government-contracting-realistic mix) across five fictional public-sector clients, each with a
role-based budget (Partner / Manager / Consultant / Associate), a contract ceiling, and, for
fixed-fee engagements, a milestone billing schedule. About 30% of engagements carry an approved
change order, which matters directly to the discrepancy checks below.

### `time_expense_tracking.py`
Generates timesheet and expense entries against every engagement's budget, spread across a
realistic staffing S-curve (ramp-up / steady-state / wind-down). About 4% of entries carry a
deliberately injected, realistic data-entry error: a missing task code, a rate that doesn't
match the person's actual labor category, an entry logged 30-90 days after the work was
performed, or time left sitting unapproved. **Nothing is pre-flagged** -- every downstream
module has to find these the way an associate would, in the raw export.

### `budget_actual.py`
For every engagement x role x month, compares budgeted to actual hours (**utilization**) and
compares the timesheet's recorded billing rate to the correct rate-card rate (**rate
realization** -- moves only when someone's time is coded under the wrong labor category). At the
engagement level, it compares % of budget consumed to % of the planned staffing curve elapsed
(earned-value logic) to flag engagements trending over budget or off pace, and separately tracks
ceiling consumption on whichever dollar basis actually matches how that contract type's ceiling
was priced (cost-plus uses cost + fee, not bill rate).

### `invoicing.py`
Drafts client invoices from reconciled T&M/cost-plus actuals or from the fixed-fee milestone
schedule, with standard professional-services line-item detail (labor by role, expenses by
category, fee/milestone lines). Every invoice traces back to the specific timesheet/expense
records it was built from; `reconcile_invoice_to_source()` independently recomputes each
invoice's total from source data. A small, realistic subset of engagements simulate a stalled
billing cycle (an admin backlog, a lapsed PO) so unbilled time actually has something real to
age into -- otherwise every eligible month gets billed the moment it closes and the aging check
below would never find anything.

### `discrepancy_detection.py` -- the core of the toolkit
Seven independent detectors, each re-deriving its finding from raw data (never from a
pre-computed flag):

| Finding | What it catches | Why it matters |
|---|---|---|
| **Missing Task Code** | Timesheet entry with no billing category | Structurally blocks that time from ever reaching an invoice |
| **Missing Approval** | Unapproved time/expense aged past a normal approval cycle | Nothing should be billable, or reimbursed, without sign-off |
| **Rate Mismatch** | Hours logged at a rate that doesn't match the recorded labor category | Distorts realization; a compliance problem if it reaches an invoice |
| **Out-of-Period Entry** | Time logged long after the work was performed | Makes prior-period budget-to-actual reporting unreliable |
| **Unbilled Time/Expense Aging** | Clean, approved, billable work not yet invoiced past a threshold age | Straight revenue leakage if left uncaught |
| **Budget Overrun (without Change Order)** | Actual spend past the authorized ceiling with no change order on file | Unauthorized cost exposure -- the highest-severity finding in the toolkit |
| **Approaching Budget Ceiling** | Spend nearing (but not yet past) the ceiling | An early warning before it becomes an overrun |

Findings are scored High/Medium/Low, sorted into a prioritized exception report, and rolled up
by engagement leader -- the exact shape of an escalation email an associate would actually send.

### `reporting.py`
Assembles the Excel workbook. Every derived figure (utilization, realization, ceiling
consumption, status, exception roll-ups) is a **native Excel formula** referencing other cells
on the workbook -- SUMIFS/COUNTIF/SUMIF/IF, nothing computed in Python and pasted as a value --
so the workbook recalculates correctly if the underlying data changes. Only source data
(budgeted hours, recorded actuals, exception findings) is written as static input.

## The Excel deliverable

`output/engagement_finance_toolkit.xlsx` (regenerated by the pipeline; the version in the repo
is the checked-in sample output):

1. **Portfolio Dashboard** -- KPI tiles (total budget, portfolio utilization, open exceptions,
   engagements over budget, etc.), a monthly utilization/realization trend line chart, a
   utilization-by-engagement bar chart, and an open-exceptions-by-severity bar chart -- all
   native openpyxl charts, not pasted images.
2. **Engagement Summary** -- one row per engagement with formula-driven KPIs, conditionally
   formatted by status (On Track / Trending Over Budget / Behind Pace / Over Budget).
3. **Budget vs Actual** -- one row per engagement x role x month.
4. **Sample Invoice** -- one fully worked time & materials invoice example, with formula-driven
   subtotals and total.
5. **Discrepancy Report** -- every open exception, conditionally formatted by severity
   (red/amber/blue), plus an escalation summary by engagement leader.

The workbook was validated with LibreOffice's headless recalculation engine: 1,271 formulas,
zero errors, and every computed KPI spot-checked against the Python pipeline's own numbers.

## The notebook

`notebooks/engagement_financial_lifecycle_walkthrough.ipynb` walks the full lifecycle end to
end, written in the voice of the engagement finance associate actually doing the work --
explaining what each check is for and why it matters, not just what the code does.

## Running it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install -e .

# Full pipeline: generates the portfolio and writes output/engagement_finance_toolkit.xlsx
python -m engagement_finance_toolkit.run_pipeline
# or, after `pip install -e .`:
engagement-finance-toolkit

# Tests (budget-to-actual ties out, every invoice reconciles to source data, etc.)
pytest tests/

# Notebook
jupyter notebook notebooks/engagement_financial_lifecycle_walkthrough.ipynb
```

The generated portfolio and every downstream figure are deterministic (seeded), so re-running
the pipeline reproduces the same numbers used throughout this README, the notebook, and the
checked-in workbook.
